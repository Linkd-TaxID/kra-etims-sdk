# Product integration through business operations

`examples/product_integration.py` runs only from a private fresh-loopback manifest produced by the companion `scripts/tests/phase-d-product.py` runner. It submits independent seller and platform-fee invoices under distinct operator-issued grants, stores both identities, performs original lookup and exact duplicate recovery, and exercises original correction, explicit stock I/O/master and local reporting. It checks sync/async behavior against independently asserted native VSCU and OSCU backends. Synthetic grants prove local routing and isolation, not consent or distinct real issuer authorization.

The companion runner builds a wheel from a private copy, installs it with `pip --no-index --no-deps --target`, and verifies imports come from that installation. Dependencies use the existing Python environment without downloading packages. HTTP probes check current Problem Details and legacy flat errors, conflict, in-flight, gateway failure, dropped response, unreadable mutation response and empty success. An unreadable mutation response is ambiguous and retains its original key. Minimum-Python declarations are not evidence of testing every interpreter; run logs should record observed interpreter versions.

Branch clients use `device:read` for `device_status()`, `capabilities()`, `device_health()`, `device_monitoring()` and `metadata("CODES"|"CLASSIFICATIONS"|"NOTICES", since=...)`. `device:initialize` separately permits `initialize_branch()` without caller-supplied PIN/serial/wire fields. Existing `DeviceInit` calls remain compatible. Capability schema v1 reports stored mode/environment, checkpoint readiness, engineering support and unavailable operations. Support does not bypass scopes, fiscal holds, exact device acceptance or production launch gates.

The accounting drill supplies the same assessed sandbox policy to both adapters. Three accountable operators assess, review and approve; immutable original deductions, refunds, batch payment references and certificate records remain supplied/unverified. Calculated withholding is not a deduction, supplied payment evidence is not verified remittance and projected payout is not paid. Control-unit selection never changes policy. No payment/submission/certificate authenticity interface is invented.

Dedicated reverse invoicing, official remittance verification and KRA withholding certificate retrieval require separately reviewed external eligibility, consent, authorization, schema and recovery contracts. The existing ordinary-sale API and original credit-note helper do not implement dedicated buyer-issued invoicing. No portal scraping is an API integration. Remote sandbox acceptance requires separate explicit authorization; none is executed by this example.
